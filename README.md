# WebSocket relay

A relay for generic WebSocket rooms and registered, owner-controlled machine bridges.

## Endpoints

The landing page at `/` supports OIDC sign-in and session management. Configure `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, and the exact public HTTPS origin as `APP_URL`. Set `AUTH_API_URL` to the corresponding authentication API origin. Register `${APP_URL}/auth/callback` as the OIDC redirect URI. Authentication fails closed when configuration is missing. Sessions use an HttpOnly, SameSite=Lax cookie and expire after eight hours.

Persistent records are stored in SQLite through the configured database provider. Set `DATABASE_URL` to its HTTPS consumer-module URL. `DB_AUTH_TOKEN` is optional: configure it only when the provider requires bearer authentication. The relay creates the required schema at startup and fails closed if the database is unavailable. Machine claims and user sessions are stored there. Existing `DATA_PATH/machines.json` and `sessions.json` files are imported once, transactionally; the originals are left untouched, and a migration marker prevents deleted records from reappearing.

`GET /api/sessions`, `POST /api/sessions` (`{ "id": "<128 lowercase hex>", "isPublic": true|false }`), and `DELETE /api/sessions/{id}` require an Auth-issued `Authorization: Bearer <access token>`. IDs are SHA-512 digests of 64 cryptographically random bytes generated by the browser. After OIDC sign-in, the page obtains short-lived API tokens directly from the configured Auth API's `POST /api/v1/session/token`, keeps them in memory, and sends them in the Authorization header. Set `AUTH_TOKEN_AUDIENCE` to the OIDC client ID, list that ID in the provider's `JWT_AUDIENCES`, and include `APP_URL` in its `AUTH_ALLOWED_ORIGINS`. Tokens are validated through the configured issuer's `/userinfo` endpoint. No Relay API token is sent to the browser.

Private sessions accept only their owner. Public sessions allow anonymous listeners, but listeners cannot publish; owner credentials may publish. Session counts include connected listeners/controllers on this relay process and expose no connection identifiers. Legacy `/new`, `/status`, and `/publish` endpoints are removed.

### [ws|wss]://host/[session-id]

Opens a WebSocket connection. All messages sent through this connection are relayed to all the other clients using the same session id.

Generic paths must match a registered 128-character lowercase hexadecimal session ID; connecting never creates a room. Machine UUID paths remain reserved and require the one-use ticket protocol below. Browser WebSocket clients may authenticate with an Authorization bearer header or `?token=`; query tokens are credentials and must not be logged.

## Machine bridge

Set `BRIDGE_REGISTRATION_TOKEN` and the distinct `RELAY_API_TOKEN`; machine operations fail closed if either is unset. `DATA_PATH` (default `/data`) is only used to discover legacy JSON files for the one-time database import.

The bridge opens `wss://host/bridge/register` with `Authorization: Bearer <BRIDGE_REGISTRATION_TOKEN>` and its first frame must be `{"type":"register","machineId":"<UUID>"}`. Successful registration replies with `type: registered`; machine UUID doubles as session ID. Bridge connections are ephemeral and duplicate live registrations are rejected.

Keep `DATABASE_URL` set and ensure the database remains available. Keep `DB_AUTH_TOKEN` set only if required by the database provider. Build and deploy the image through the project's configured CI pipeline.

Admin endpoints require `Authorization: Bearer <RELAY_API_TOKEN>`:

- `GET /_admin/machines` lists registry records and current online state.
- `POST /_admin/machines/{uuid}/claim` with `{"ownerSub":"OIDC subject"}` claims once; repeating the same claim is idempotent, other owners receive 409.
- `POST /_admin/machines/{uuid}/ticket` with the same owner returns a random one-use ticket, valid for at most 60 seconds.

The UI connects to `wss://host/{machineId}` and must send `{"type":"authorize","ticket":"..."}` as its first frame within five seconds. Only one UI controller may connect. On authorization it receives an `authorized` acknowledgement; subsequent text and binary frames are relayed unchanged between controller and bridge. Never log or persist tickets. Both peers are disconnected when the other disconnects.

## Usage

```js
const alice = new WebSocket("ws://host:port/61e851ce-4b2e-42f3-8ae8-5f4944a1b8f5");
const bob = new WebSocket("ws://host:port/61e851ce-4b2e-42f3-8ae8-5f4944a1b8f5");

alice.onmessage = (event) => console.log("Alice received:", event.data);
bob.onmessage = (event) => console.log("Bob received:", event.data);

alice.send("Hi Bob!");
// Bob received: Hi Bob!

bob.send("Hi Alice!");
// Alice received: Hi Alice!
```
